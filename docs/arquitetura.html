Arquitetura do acervo

Um cofre de PDFs digitalizados, separado por município, caixa, tipo e ano, com busca no acervo inteiro e busca dentro de cada documento sem abrir o arquivo. Três níveis de acesso: você (admin), o cliente que contrata e os leitores que o cliente cadastra.

react + vitesupabase · postgresbusca full-text em portuguêsworker de OCR em pythonarquivos privados com link temporário
[01] quem faz o quê

Três papéis, uma regra

Cada cliente é uma organização. Você libera partes do acervo para a organização; o cliente e os leitores dele enxergam só o que foi liberado. Ninguém de fora da organização vê nada dela.

papel: admin
Você

Dono do acervo. Único que mexe nos arquivos.

  • Envia, edita metadados e remove PDFs
  • Cria clientes (organizações)
  • Concede e revoga acesso por município, caixa ou documento
  • Vê o registro de quem abriu e baixou o quê
papel: cliente
Cliente

Quem recebe o app. Ex.: uma prefeitura ou um escritório contábil.

  • Busca e visualiza os documentos liberados
  • Cria e desativa leitores da própria organização
  • Não envia nem apaga arquivos
papel: leitor
Leitor

Funcionário cadastrado pelo cliente.

  • Busca e visualiza o mesmo acervo do cliente
  • Não cria usuários
  • Não envia nem apaga arquivos

[02] como o acervo se organiza

Município, caixa, documento

A caixa espelha a caixa física do arquivo. Tipo e ano são atributos do documento, então funcionam como filtro em qualquer nível: "todas as leis de 2016 de Santa Rita", "tudo da caixa 012".

Filtros da busca: município, caixa, tipo, ano (exato ou intervalo) e texto livre. Cada filtro mostra quantos documentos sobram, para você ver na hora onde está o volume.

Metadado no upload: no envio em lote, o sistema tenta ler município, caixa, tipo e ano do caminho do arquivo, por exemplo SANTA-RITA/CX-012/2016_LEI_045.pdf. Você confere numa tabela e confirma antes de processar.

[04] do upload até a busca

O que acontece com cada PDF

Tudo que deixa a consulta rápida é calculado uma vez, no envio. Na hora da busca, o sistema não abre PDF nenhum: lê texto e imagens que já estão prontos.

  1. [1] envio
    Upload em lote

    Admin arrasta pastas. O arquivo vai direto para o storage privado e entra na fila com status na_fila.

  2. [2] duplicado
    Confere o hash

    SHA-256 do arquivo. Se o mesmo PDF já existe, avisa em vez de duplicar.

  3. [3] texto
    Tem camada de texto?

    Se o PDF é só imagem, passa pelo OCR em português. Se já tem texto, pula essa etapa.

  4. [4] páginas
    Texto por página

    Cada página vira uma linha no banco com seu texto. É isso que permite dizer "achei na página 7".

  5. [5] miniaturas
    Capa e páginas

    Capa em 320 px e cada página em 160 px, em WebP. Uma página digitalizada vira uns 8 KB.

  6. [6] índice
    Indexação

    Postgres gera o índice de busca em português, sem acento e tolerante a erro de OCR.

  7. [7] pronto
    Liberado na busca

    Status vira pronto. Com erro, vira erro e aparece no painel do admin para reprocessar.

  8. [8] acesso
    Herdado

    Quem tem acesso ao município ou à caixa já enxerga o documento novo, sem configurar nada.

// nível 1 · busca no acervo

Filtros viram cláusulas SQL simples; texto livre procura no índice das páginas e agrupa por documento, ordenando por relevância.

A grade carrega só miniaturas de 8 KB, então 200 resultados aparecem quase na hora. A permissão é aplicada pelo próprio banco (RLS): mesmo que o front erre, o banco não devolve o que a pessoa não pode ver.

// nível 2 · busca dentro do documento

Uma consulta nas páginas daquele documento só. Devolve número da página, trecho com o termo destacado e a miniatura. Responde enquanto você digita.

Clicou no trecho, abre o visualizador direto naquela página com o termo marcado. O PDF só é baixado nesse momento, e por link temporário.

// a consulta do nível 2, para referência

select numero,
       ts_headline('pt', texto, q, 'MaxFragments=2') as trecho,
       miniatura_path
  from paginas, websearch_to_tsquery('pt', unaccent(:termo)) q
 where documento_id = :doc and tsv @@ q
 order by ts_rank(tsv, q) desc;   -- 'pt' = configuração portuguese + unaccent

[07] segurança

Quem não pode ver, não recebe

São documentos públicos de prefeitura, mas o acervo é o seu produto. A regra de acesso fica no banco, não só na tela.

// rls no postgres

Uma função pode_ver(documento) é usada em documentos, paginas e miniaturas. Admin vê tudo; os demais só quando existe um acesso da organização que cubra o município, a caixa ou o documento.

// arquivos privados

Bucket sem acesso público. Miniaturas e PDF chegam por link assinado que expira em 5 minutos, gerado depois de checar a permissão.

// criação de usuários

Feita por uma edge function: confere se quem pede é admin, ou cliente criando leitor da própria organização. A chave de serviço nunca vai para o navegador.

// rastro

Toda visualização, download e busca vai para a auditoria. Desativar um usuário corta o acesso na hora, sem apagar o histórico.

[08] ordem de construção

Front primeiro, back encaixa depois

O front nasce com dados falsos atrás de uma camada api/. Quando o Supabase entrar, troca-se só essa camada; as telas ficam como estão.

F0
Front navegável próximo

Login, busca com filtros, grade de miniaturas, painel com busca interna, visualizador, painéis de admin e de equipe. Seletor para trocar entre os três papéis e testar o que cada um vê.

F1
Banco e login

Projeto Supabase, as nove tabelas, RLS, bucket privado, convite por e-mail. Front passa a usar dados reais.

F2
Worker de ingestão

OCR, texto por página, miniaturas, fila com reprocessamento. Teste com uma caixa real.

F3
Busca de verdade

Índice em português sem acento, contagem por filtro, busca interna com destaque, abrir PDF na página certa.

F4
Gestão

Clientes, leitores, concessão de acesso em lote, auditoria com filtros.

F5
Produção

Domínio próprio, backup diário, carga do acervo inteiro, ajuste de desempenho com o volume real.

[09] decisões em aberto ✦

O que eu preciso de você

As respostas mudam o banco e a tela, por isso vêm antes do código. Onde não houver resposta, sigo a sugestão entre parênteses.

  1. [a]
    Os PDFs já têm texto?

    Se dá para selecionar o texto no PDF, pulamos o OCR. Se são só imagem, o worker faz o OCR. (sugestão: suportar os dois)

  2. [b]
    Caixa é a caixa física?

    Uma caixa pertence a um único município? Pode misturar anos? (sugestão: sim e sim)

  3. [c]
    Você libera o quê para o cliente?

    Município inteiro, caixas soltas ou documentos avulsos? (sugestão: os três, município como padrão)

  4. [d]
    Leitor vê tudo do cliente?

    Ou o cliente escolhe um recorte para cada leitor? (sugestão: vê tudo, recorte depois se precisar)

  5. [e]
    Pode baixar e imprimir?

    Cliente e leitor baixam o PDF ou só visualizam? Marca d'água com o nome de quem baixou?

  6. [f]
    Qual o volume?

    Quantos PDFs e páginas, mais ou menos. Até ~100 GB o storage do Supabase Pro resolve; acima disso, PDFs vão para o Cloudflare R2.

  7. [g]
    Os arquivos seguem um padrão de nome?

    Se as pastas já estão como município/caixa/arquivo, o upload em lote preenche os metadados sozinho.

  8. [h]
    Qual visual o app usa?

    Sua identidade (editorial + terminal) ou o corporativo que usamos no controle de viagens, já que vai para cliente?
